# 资产文档制作标准(可解析规范)v1

> 本规范是**权威依据**。所有剧集的资产描述文档(界面「资产描述」框 /
> `eXX_asset_description.md`),无论人工撰写还是 AI 生成,一律按此写。
> 照此写,解析器可**确定性**识别 人物 / 场景 / 道具 / 插入,不会出现
> "人物被解析成道具""台词碎片被当人物"这类失误。
>
> 规范与解析器代码一一对应(`server.js`):`structuredAssetType`(段标题→类型)、
> `parseStructuredAssetDescriptions`(主循环)、`isStructuredAssetMarkerLine`(条目边界)、
> `structuredAssetLabel`(名称截取)。**改规范前先改解析器并加回归测试。**

## 0. 一句话原则

用 `◆ XX卡` 分段;段内每个资产用**带圈序号行**起头,该行**开头就是干净的资产名**;
其余描述全部用 `· 字段：值` 写。**段标题决定类型;序号行决定"新资产";`·` 行永远是从属描述。**

## 1. 为什么必须这么写(失误根源)

解析器有两种模式:
- **卡片模式**——段标题以 `◆` 开头且含「卡」或「card」时触发。此模式下**只有序号行才新建资产**,
  其余所有行都并入当前资产。**最安全,本规范强制使用。**
- 松散模式——没有 `◆...卡` 标题时,解析器只能**靠名字猜类型**(名字带「针/刀/石/环」猜道具、
  带「厅/楼/城/院」猜场景、带「·」猜场景)。**极易出错,禁止依赖。**

奶奶上膛事故根源:用了 `◆ 人物卡 CHARACTERS`(触发了卡片模式),但角色行没用序号,
导致 `中文提示词：`、`EN prompt:` 被当成新资产、9 个角色反被挤成道具/场景/插入。
只要角色行前面加上序号(`① NANA`),问题即根除。

## 2. 标准骨架(复制这个改)

```
◆ 全局画风锚
（这里写整体画风、调色板等全局说明。标题不含「卡」字,不会被当成资产。）

◆ 人物卡 CHARACTERS
① NANA（阿格妮丝 / 代号 PURL）
· 一句话：全世界最人畜无害的烤饼干老太太,其实是头号杀手。
· 外观：约70岁,银白卷发挽成松髻,圆脸笑纹,金丝老花镜。
· 服装：芥末黄针织开衫 + 碎花围裙。
· 标志物：钛合金毛衣针(既是道具也是凶器)。
· 中文提示词：皮克斯风格3D渲染,约70岁和蔼老奶奶……竖屏9:16。
· EN prompt: Pixar-style 3D render, a kindly ~70-year-old grandmother… vertical 9:16.

② DYLAN（迪伦·男主搭档）
· 外观：约25岁男性,黑色连帽衫,神情警惕。
· 中文提示词：……

◆ 场景卡 SCENES
① 安全屋 SAFEHOUSE（团队藏身处·夜）
· 外观：地下室改造,暖光,墙上贴满线索照片。
· 中文提示词：……

◆ 道具卡 PROPS
① 来电手机（老式翻盖机·剧情关键道具）
· 外观：老式翻盖机,屏幕显示未知号码。
· 中文提示词：……

◆ 插入卡 INSERTS
① 释放按钮特写（金属面板红色圆钮）
· 外观：金属面板上的红色圆钮,微微反光。
```

> ⚠️ 每个序号条目名后都带 `（…）` 括注——这是**硬性要求**(见 R2b)。
> 缺括注时,名字不以特定字结尾的场景/道具/插入会被解析器**静默丢弃**。

## 3. 硬规则(违反即解析出错)

### R1 段标题(决定类型)
- 必须以 `◆` 开头,且含「卡」或「card」→ 才触发卡片模式。
- 类型关键词(中英任选,大小写随意):
  - 人物段:`人物卡` / `角色卡` / `人物卡 CHARACTERS`
  - 场景段:`场景卡` / `环境卡` / `地点卡` / `场景卡 SCENES`
  - 道具段:`道具卡` / `物件卡` / `道具卡 PROPS`
  - 插入段:`插入卡` / `细节卡` / `特写卡` / `插入卡 INSERTS`
- 全局说明段(画风、调色板)用**不含「卡」字**的 `◆ 标题`(如 `◆ 全局画风锚`);
  解析器遇到它会清空当前分区,段内内容不会被当资产。

### R2 资产条目行(决定"这是一个新资产")
- 每个资产**必须**以带圈序号或数字序号起头,且序号后紧跟资产名:
  - 支持:`①`–`⑳`、`㊀`–`㊉`,或 `1. ` / `1) ` / `1、`(数字后跟 `.` `)` `、` `．` `）`)。
- 序号行**开头就写干净的资产名**。名称截取规则(务必知道):
  - 解析器取序号后的文本,**遇到第一个 `：`、`，`、`。`、`；`、`（` 就截断**。
  - 所以 `① NANA（阿格妮丝/代号PURL）` → 名称=`NANA`(括号及之后被切掉,别名放括号里安全)。
  - **反例**:`① 一位约70岁的老奶奶,银白卷发` → 名称会变成`一位约70岁的老奶奶`(垃圾名)。
    正确写法:`① NANA` 起头,描述放到下面的 `·` 行。

### R2b 序号行必须带 `（…）` 括注(硬性,最易漏)
- **每个序号条目名后都要跟一个 `（…）` 括注**(写别名、定位、代号、一句话身份均可)。
- 原因(解析器真实行为):卡片模式下,序号行仍会经过 `structuredSectionAssetEntry` 的
  "名字猜类型"启发式——场景名须以 `厅/楼/城/院/室/站…` 等字结尾、道具名须以 `刀/石/器/针…`
  结尾,否则**被静默丢弃**。而只要该行带 `（…）` 括注,`hasParentheticalIdentity` 命中,
  **直接判为资产、跳过名字启发式**——这是最可靠的通道。
- 实测:`① 安全屋 SAFEHOUSE`(无括注)→ 场景丢失;`① 安全屋 SAFEHOUSE（团队藏身处·夜）`
  → 正确识别为 Scene。人物名(英文名/中文人名)通常能过启发式,但**场景/道具/插入几乎必须带括注**。
- 结论:**四类资产的序号行一律带括注**,最省心、零丢失。

### R3 描述字段行(永远从属于当前资产,绝不新建资产)
- 卡片模式下,**任何不以序号起头的行都会并入当前资产**——这是安全底线。
- 但为清晰、且兼容非卡片场景,一律用以下两种写法之一:
  - **推荐**:`· 字段：值`(圆点起头,解析器 `structuredSectionAssetEntry` 直接判为从属描述)。
  - 或白名单字段名起头(解析器显式识别为字段,不当资产):
    `一句话` `外观` `身份` `造型` `年龄` `体型` `脸型` `发型` `服装` `气质` `神态`
    `空间` `氛围` `灯光` `材质` `纹理` `结构` `用途` `特征` `构图` `时间` `天气` `色彩`
    `标志物` `生理线` `配色` `一致性锚点` `中文提示词` `EN prompt` `关键变体` `关键元素`
    `光线氛围` `定位` `核心美学` `调色板逻辑`(后跟 `：`/`:`)。
- **锁定生图提示词**(可选但推荐):用 `· 中文提示词：…` 和 `· EN prompt: …` 直接给,
  这样生图不靠模型再补,画面最可控。多个变体分多行:`· 中文提示词（日常态）：…`。

### R4 名称唯一 & 别混写
- 同类型下资产名不要重复(解析器按 `label` 去重,重名会被吞)。
- **一份文档只用卡片式**。不要在同文档里混入"手动提示词块(`1. 名称`+空行+`提示词：`)"或
  纯松散叙事——它们走不同解析分支,会互相打架。

## 4. 提交前自检清单(照着勾)
- [ ] 每个类型段都有 `◆ …卡 …` 标题(含「卡/card」)。
- [ ] 每个资产都以 `①…`/`1.` 序号起头,序号后**第一个词就是资产名**。
- [ ] 资产名里没有逗号/句号/冒号(别名、代号放 `（）` 里)。
- [ ] **每个序号行名字后都带 `（…）` 括注**(R2b,场景/道具/插入尤其不能漏,否则静默丢失)。
- [ ] 所有描述都是 `· 字段：值` 行,没有裸描述行冒充资产。
- [ ] 人物段只放人、场景段只放地点、道具段只放物件——**不靠名字,靠段归属**。
- [ ] 全局说明用不含「卡」字的 `◆ 标题`。
- [ ] 需要精确画面时,给了 `· 中文提示词：` / `· EN prompt:`。

## 5. 典型错误 → 正确对照
| 错误写法 | 后果 | 正确写法 |
|---|---|---|
| `NANA / 阿格妮丝`(无序号,在人物卡内) | 被当描述行或漏解析 | `① NANA（阿格妮丝）` |
| `① 一位70岁老奶奶,银发` | 名称=`一位70岁老奶奶` | `① NANA` + `· 外观：70岁,银发` |
| `中文提示词：…`(顶格,无 `·`,非卡片模式) | 被当成新资产 | `· 中文提示词：…` |
| 场景写进 `◆ 人物卡` 段 | 被判成 Character | 移到 `◆ 场景卡` 段 |
| `标志物：毛衣针` 单独成行顶格 | 可能被当道具资产 | `· 标志物：毛衣针`(并入角色) |
| `① 安全屋 SAFEHOUSE`(无括注) | 场景被**静默丢弃** | `① 安全屋 SAFEHOUSE（团队藏身处·夜）` |
| `① 来电手机`(无括注) | 道具被丢弃 | `① 来电手机（老式翻盖机）` |

## 6. 已知解析器缺陷(文档规避不了,靠审核关兜底)
- **硬编码项目正则会造幽灵资产**:`buildRuleAssets` 里有几十条针对旧剧本的正则
  (`手机/电话/未知号码 → 未知号码电话插入镜头`、`照片/2005 → 剧情旧照片`、`Ω核心`、
  `Hale Tower 冷蓝能源纹路` 等)。只要你文档里出现这些词,即便没在道具卡里列,
  也会**凭空多出一个资产**。这是解析器历史欠债,**写法无法规避**。
- 缓解:运行时交叉审核关会把这类多余/重复资产标出;长期应清理这些硬编码正则(单列技术债)。

## 7. 与其他防线的关系
本标准是**第一道防线**(写的时候就不出错)。另有:
- 解析器卡结构修复(已上线):即便偶有偏差也按段归属锁定类型。
- 运行时交叉审核关:解析结果由第二个模型复核分类,审核完成才交付。
三者叠加,资产误分类风险降到最低。
